# Hybrid search parity demo: SQL Server vs PostgreSQL

- **Status:** design approved in brainstorming, awaiting spec review
- **Date:** 2026-10-20
- **Branch:** `feature/postgres-hybrid-search-demo`, on the fork only. It is never merged upstream.
- **Base commit:** `9f8cd102`. Production code is copied from this commit, and the docs corpus is read from it.

## 1. Purpose

Answer one question with evidence: **can GuideAnts' hybrid search (full-text + vector) move from SQL Server to PostgreSQL and give the same results?**

The deliverable is a small .NET demo plus a committed `RESULTS.md` containing a verdict. The demo:
- loads byte-identical data into both databases;
- runs production's exact SQL Server query against a Postgres port;
- applies parity rules decided in advance;
- explains every difference.

The application code that runs a search does not know which database it is using. Configuration alone decides.

This is an experiment, not production work. If the verdict is "switchable", the Postgres search code becomes a starting point for a real migration. That migration has its own design and PR, and touches the data model, migrations and the other SQL Server-only code listed in earlier research.

## 2. The verdict

`compare` reports **switchable** only when all five conditions hold:

1. **Vector parity passes:** rule 1 in section 7.
2. **Every full-text match difference, and every error that happens on only one side, is reviewed and accepted:** rule 2 and section 6.5. None is unreviewed or marked `blocker`.
3. **Mean top-5 hybrid overlap is at least 0.9**, across all query/scope pairs that count toward the verdict.
4. **The #1 hybrid result is the same in at least 80%** of those pairs (equal-score groups count as the same).
5. **Zero unexplained hybrid differences:** rule 3.

The thresholds live in `appsettings.json` and are committed before the first `compare` run. `RESULTS.md` prints them, together with the sample's git commit. If `appsettings.json` has uncommitted changes, it prints a warning that the thresholds were modified.

The verdict judges:
- the `sqlserver` profile (baseline) against the `postgres` profile (candidate);
- production's search behaviour as it is today, including the top-N quirk (section 6.3);
- saved queries only.

Everything else is informational:
- the quirk-fixed run;
- the `postgres-english` profile;
- live queries.

## 3. Scope

**In scope**

### 4.1 Contracts (in `Parity.Core`)

**`ISearchStore`** is the only thing the search path depends on:
- `EnsureSchemaAsync(ct)`: drop and recreate the table and the full-text objects.
- `LoadAsync(IReadOnlyList<ChunkRecord>, ct)`: bulk-insert chunks with their vectors.
- `WaitUntilSearchableAsync(ct)`: block until full-text indexing has finished. This is a real wait on SQL Server and returns immediately on Postgres.
- `HybridSearchAsync(HybridQuery, ct) → IReadOnlyList<SearchHit>`: production's algorithm.

**`ISearchDiagnostics`** is used only by `compare` and the tests:
- `VectorSearchAsync(vector, Scope, k, ct) → IReadOnlyList<VectorHit>`: exact cosine top-k within a scope.
- `TextMatchAsync(text, Scope, ct) → IReadOnlyList<TextMatch>`: the full phrase-match set within a scope, with the engine's raw rank and no top-N limit.
- `ScoreChunksAsync(HybridQuery, chunkIds, ct) → IReadOnlyList<ChunkScore>`: for each chunk, what the hybrid query would compute:
  - vector score and text score;
  - whether it matched the phrase;
  - its raw rank;
  - whether it made the top-N candidate set, and the rank of the N-th candidate.
- `TokenizeAsync(text, ct) → IReadOnlyList<Token>`: how the engine breaks text into words. SQL Server uses `sys.dm_fts_parser`; Postgres uses `ts_debug`.
- `DescribeAsync(ct) → EngineInfo`:
  - SQL Server: `@@VERSION` and the full-text language and stoplist;
  - Postgres: `version()`, the `pgvector` extension version, and the text search configuration.

**Records:**
- `ChunkRecord` (id, indexName, projectId, notebookId, documentId, sourcePath, chunkIndex, kind, content, embedding)
- `HybridQuery` (text, vector, scope, maxResults, vectorWeight, textWeight, candidateMultiplier, filterBeforeTopN)
- `Scope` (indexName, notebookId?)
- `SearchHit` (chunkId, content, contentFileId, notebookFileId, chunkIndex, indexName, vectorScore, textScore, score)

`SearchHit` has the same fields as production's `HybridSearchResult`.

Added during planning:
- `ISearchStore.PingServerAsync` (connect to the server, not the database, so "not running" can be told apart from "not seeded");
- a `createdUtc` argument on `LoadAsync`;
- `ISearchDiagnostics.GetIndexCoverageAsync`, which returns row and indexed-row counts for the sanity checks;
- a `Normalized` field on `Token`.

`search` treats text as a saved query only when it equals a saved query's text exactly after trimming; the comparison is case-sensitive. Tests use xUnit with its built-in asserts.

The query methods listed above (`HybridSearchAsync`, `VectorSearchAsync`, `TextMatchAsync`, `ScoreChunksAsync`, `TokenizeAsync`) actually return `EngineResult<T>`. That's either the value shown or an `EngineError` (engine error number or SQLSTATE, plus the message). So when a database rejects a query, the caller gets the error, never an empty list that looks like "no results" (section 6.5). Schema, load and connection failures are thrown as exceptions and stop the command (section 11).

## 5. Data

### 5.1 Corpus

- **Documents:** the 79 top-level `docs/*.md` files at commit `9f8cd102` (1,194,882 bytes), read with `git show 9f8cd102:<path>`. Untracked files and uncommitted edits can never get in. The commit is recorded in `manifest.json`.
- **Preparation copied from production:**
  - `HybridIndexer.ChunkText`: 2,048-byte UTF-8 chunks with 50% overlap, including its early-exit rule and its habit of splitting multi-byte characters;
  - `MarkdownInlineImageSanitizer`, applied before chunking, exactly as `IndexContentFileAsync` does.

  This gives roughly 1,170 chunks. The copied files carry a header naming their source file and commit.
- **Edge cases:** the 20 hand-written chunks in Appendix B are added as single chunks with `kind = "edge"`.

### 5.2 Projects, notebooks and IDs

- **Three synthetic projects, P1, P2 and P3.** Each `ProjectId` is a name-based GUID (RFC 4122 v5, with a fixed namespace) derived from `project:P1` and so on. `IndexName` is the project ID as a string, as in production.
- **One notebook, N1, in P1.**
- **File assignment:** doc files are sorted ordinally by path, and file *i* goes to project `P((i mod 3) + 1)`. Every third file assigned to P1 also gets `NotebookId = N1`.
- **Edge-case assignment:** edge case *Ej* goes to project `P(((j − 1) mod 3) + 1)`.
- **Chunk IDs** are v5 GUIDs of `doc:<path>#<chunkIndex>` or `edge:<Ej>`. Both databases therefore hold the same IDs, and regenerating from the same commit reproduces them.
- **`DocumentId`** is the source path.
- **`ContentFileId`** is a v5 GUID of the path. That keeps the column populated the way production's is.
- **`NotebookFileId` and `AssistantFileId`** are null.
- **`CreatedUtc`** is fixed at the generation time recorded in the manifest.

### 5.3 Embeddings

- **Model:** OpenAI `text-embedding-3-small` at its native 1536 dimensions, so no padding is needed.
- **Key:** read from `OPENAI_API_KEY`, or from `dotnet user-secrets`. It's never committed.
- **What gets embedded:** every chunk and every saved query, in batches of 100, with retry and backoff on rate-limit and transient errors.
- **Format:** vectors are stored exactly as returned, as float32. Generation fails if any vector isn't 1536 values or contains a non-finite value.

### 5.4 Files

| File | Contents |
|---|---|
| `inputs/edge-cases.json` | Hand-written, reviewed edge-case chunks: Appendix B |
| `inputs/queries.json` | Hand-written, reviewed saved queries: Appendix A, with `id`, `group`, `text` and optional expectations |
| `data/chunks.jsonl` | One JSON object per chunk: id, indexName, projectId, notebookId, documentId, contentFileId, sourcePath, chunkIndex, kind, content. About 2.5 MB |
| `data/embeddings.f32` | Raw little-endian float32, `N × 1536`, in `chunks.jsonl` order. About 7.2 MB |
| `data/query-embeddings.f32` | The same format, in `queries.json` order |
| `data/ground-truth.json` | The ground-truth match set for each exact-phrase and edge-case query (see below) |
| `data/manifest.json` | Corpus commit, generation time, model, dimensions, counts, SHA-256 of every data and input file, and the SHA-256 of each copied production source file |

`seed` checks the manifest hashes before loading and refuses to load a set of files that's mismatched or incomplete.

For each exact-phrase and edge-case query, `generate-data` also records a **ground-truth match set**: chunks whose text contains the phrase as a whole-word, case-insensitive, whitespace-flexible regex match. This oracle is independent of both engines and is used only for the sanity checks in section 9.2, never in the parity rules.

### 5.5 Seeding

`seed --profile <name>` (or `--all`) does the following in order:
1. Verify the data files.
2. `EnsureSchemaAsync`.
3. `LoadAsync`.
4. `WaitUntilSearchableAsync`.

On SQL Server, step 4 polls these until all three hold, or fails after a timeout:
- `FULLTEXTCATALOGPROPERTY('DocumentChunks_Catalog','PopulateStatus') = 0`
- `OBJECTPROPERTYEX(OBJECT_ID('DocumentChunks'),'TableFulltextPendingChanges') = 0`
- `OBJECTPROPERTYEX(OBJECT_ID('DocumentChunks'),'TableFulltextItemCount')` equals the row count

## 6. Search implementations

### 6.1 Shared table

EF Core creates the table with `EnsureCreated`, from an entity copied from production's `DocumentChunk` without navigation properties. It has the same columns, types and primary key name, `PK_DocumentChunks`, and `Embedding` stays a `float[]`.

**SQL Server**
- Uses `UseVectorSearch()`, giving a `vector(1536)` column, as production does.
- After `EnsureCreated`, the store runs production's full-text DDL from `LiteBaselineV1` verbatim: `CREATE FULLTEXT CATALOG DocumentChunks_Catalog`, then `CREATE FULLTEXT INDEX ON DocumentChunks(Content) KEY INDEX PK_DocumentChunks ON DocumentChunks_Catalog`. This keeps the server's default full-text language and the system stoplist.
- Unlike production, it **fails** if `FULLTEXTSERVICEPROPERTY('IsFullTextInstalled') = 0`. Silently skipping the index would make both sides "match nothing" and pass falsely.

**Postgres**
- Uses `UseVector()` and `HasPostgresExtension("vector")`.
- `Embedding` maps to `vector(1536)` through a value converter from `float[]` to `Pgvector.Vector`. That's the smallest entity change a real migration would need.
- After `EnsureCreated`, the store adds:
  - the text search configuration (section 6.3);
  - `"ContentTsv" tsvector GENERATED ALWAYS AS (to_tsvector('<config>', "Content")) STORED`;
  - a GIN index on `"ContentTsv"`.
- There's no vector index.

### 6.2 SQL Server: production's query, copied exactly

`SqlServerSearchStore.HybridSearchAsync` contains the SQL text and escaping from `HybridSearcher.SearchAsync` at `9f8cd102`, copied exactly:
- the JSON-cast `@queryVec vector(1536)`;
- the `TextScores` CTE with `LEFT JOIN CONTAINSTABLE(DocumentChunks, Content, '<escaped phrase>', <maxResults × 2>)`;
- `RANK / 1000.0` as the text score;
- `1 - vector_distance('cosine', …)` as the vector score;
- the weighted score;
- `WHERE TextScore > 0 OR vector_distance(...) < 1.0`;
- `ORDER BY Score DESC`.

Production's quote-doubling and its string building are kept, because they're part of the behaviour being measured. The only difference is that the store returns a database error as an error result instead of swallowing it (section 6.4).

**Diagnostics**
- `VectorSearchAsync`: `TOP (@k)` ordered by `vector_distance('cosine', …)`, within the scope.
- `TextMatchAsync`: `CONTAINSTABLE` with the same escaped phrase and no `top_n`, joined to the scope.
- `ScoreChunksAsync`: recomputes the hybrid CTE for the requested IDs and reports whether each was in the top-N candidates.
- `TokenizeAsync`: `sys.dm_fts_parser(N'"<phrase>"', <full-text language>, 0, 0)`.

### 6.3 Postgres: the port

- **Text search configuration `parity_english_nostem`.** Its goal is to drop English stop words, as SQL Server's system stoplist does, without stemming, since SQL Server's phrase search matches whole words only.

  ```sql
  CREATE TEXT SEARCH DICTIONARY parity_simple_english (TEMPLATE = pg_catalog.simple, STOPWORDS = english);
  CREATE TEXT SEARCH CONFIGURATION parity_english_nostem (COPY = pg_catalog.simple);
  ALTER TEXT SEARCH CONFIGURATION parity_english_nostem
    ALTER MAPPING FOR asciiword, word, numword, asciihword, hword, numhword, hword_asciipart, hword_part, hword_numpart
    WITH parity_simple_english;
  ```

  The `postgres-english` profile uses the stock `english` configuration instead, in its own database.

- **Hybrid query.** The structure follows production's step by step:

  ```sql
  WITH q  AS (SELECT phraseto_tsquery(@cfg::regconfig, @query) AS tsq),
       ft AS (SELECT dc."Id", ts_rank_cd(dc."ContentTsv", q.tsq, 32) AS rank
              FROM "DocumentChunks" dc, q
              WHERE dc."ContentTsv" @@ q.tsq
              ORDER BY rank DESC
              LIMIT @candidateLimit),                      -- across all projects, like CONTAINSTABLE top_n
       scored AS (SELECT dc.*, COALESCE(ft.rank, 0) AS "TextScore",
                         1 - (dc."Embedding" <=> @vec) AS "VectorScore"
                  FROM "DocumentChunks" dc LEFT JOIN ft ON ft."Id" = dc."Id"
                  WHERE dc."IndexName" = @indexName
                    AND (@notebookId IS NULL OR dc."NotebookId" = @notebookId))
  SELECT …, @vw * "VectorScore" + @tw * "TextScore" AS "Score"
  FROM scored
  WHERE "TextScore" > 0 OR (1 - "VectorScore") < 1.0
  ORDER BY "Score" DESC
  LIMIT @maxResults;
  ```

- **Parameters.** The query text and vector are passed as parameters, not built into the SQL string. This is safer and doesn't affect results.
- **Text score.** `ts_rank_cd(…, 32)` gives `rank / (rank + 1)`, between 0 and 1. Its spread differs from SQL Server's `RANK / 1000`, and that difference is what rule 3 measures.
- **Diagnostics:** the same shapes as SQL Server. `TokenizeAsync` uses `ts_debug(@cfg::regconfig, @text)`, and `TextMatchAsync` uses `ts_rank_cd` with no `LIMIT`.

### 6.4 The quirk-fixed variant

`HybridQuery.FilterBeforeTopN = true` applies the scope filter *before* choosing the top N text candidates, on both engines:
- **SQL Server:** a `TOP (@candidateLimit)` subquery over `CONTAINSTABLE` joined to `DocumentChunks` and filtered by scope.
- **Postgres:** the scope `WHERE` moves into the `ft` CTE.

It's used only for the informational section, and it's labelled "not production" wherever it appears.

### 6.5 Errors and ties

- **Errors.** Production catches every exception and returns an empty list. So, for example, if SQL Server rejects a full-text predicate, the user gets no results at all, vector results included.
  - The stores return a typed error result instead.
  - `search` prints what production would show (an empty result) plus the error.
  - `compare` treats an error as its own outcome. An error on one side is reviewed through `known-differences.json` with category `error-handling`, and those query/scope pairs are left out of the hybrid metrics.
- **Ties.** Hits whose scores are within `TieTolerance` of each other form a group. Reordering within a group is not a difference, and production's `ORDER BY` has no tie-breaker anyway.

## 7. Comparison: rules, explanations and the report

`compare` runs every saved query in four scopes (P1, P2, P3, and P1/N1), against the baseline and the candidate. That's 38 × 4 = 152 query/scope pairs.

### 7.1 Rule 1: vector parity (must pass)

For each pair:
- `VectorSearchAsync` with `k = 10` must return the same IDs in the same order, allowing reordering within tie groups.
- Every score must agree within `VectorTolerance` (1e-5).
- Each hybrid hit's `vectorScore` is checked the same way.

Any failure fails the verdict, and the report shows both lists side by side.

### 7.2 Rule 2: full-text match parity (must pass, with reviewed exceptions)

For each pair, the two `TextMatchAsync` ID sets must be equal. For any difference, the report shows:
- the chunks only the baseline matched and the chunks only the candidate matched, each with a snippet around where the phrase is expected;
- `TokenizeAsync` output from both engines for the query and for the snippet, so the cause is visible.

A difference must match an entry in `known-differences.json` (section 7.4) whose decision is `acceptable`; otherwise it fails the verdict.

### 7.3 Rule 3: hybrid ranking (measured, explained)

For each pair that counts toward the verdict (no error on either side), the report shows:
- **overlap@5**: `|A ∩ B| / 5`, where A and B are the top-5 IDs from each side. A chunk in A but not in B still counts as overlapping when, on B's side, it ties with B's 5th hit. Ties at the cut-off are arbitrary on both engines. When fewer than 5 hits exist on both sides, the denominator is the larger of the two counts;
- **same #1**: B's #1 hit is A's #1, or ties with it on A's side;
- each chunk's rank on both sides.

Each chunk that is in one top 5 and not the other, or that moves outside its tie group, is classified using `ScoreChunksAsync` from both sides. Rule 1 guarantees the vector scores are equal, so any score gap is `textWeight × Δ text score`.

| Category | Condition |
|---|---|
| `scored-differently` | Both engines matched the chunk and both kept it in the top-N candidates, but their text scores differ |
| `matched-one-side` | Only one engine matched it. This links to the rule 2 entry |
| `top-n-cut` | Both matched it, but only one kept it among the top `maxResults × 2` candidates (chosen across all projects) |
| `top-n-boundary-tie` | Like `top-n-cut`, but on the side that cut it, its raw rank equals the N-th candidate's rank, so the choice was arbitrary |
| `displaced` | The chunk's own scores are equal on both engines, but it moved because other chunks' scores changed. It counts as explained only when the same pair has at least one difference in one of the categories above; otherwise it's unexplained |
| **unexplained** | Anything else, such as differing vector scores, or a displacement with no cause in the pair. This fails the verdict |

A chunk in one top 5 whose score on the other side ties with that side's 5th hit is not a difference, since the cut-off between tied chunks is arbitrary on both engines.

### 7.4 `known-differences.json`

There's one entry per query and scope, for full-text differences and for errors:

```json
{
  "queryId": "Q19",
  "scope": "P2",
  "kind": "text-match",
  "baselineOnly":  ["<chunk id>", "…"],
  "candidateOnly": ["<chunk id>"],
  "category": "tokenization",
  "reason": "SQL Server splits text-embedding-3-small into four words; Postgres keeps hyphenated words as one token plus its parts.",
  "decision": "acceptable",
  "reviewedBy": "…",
  "reviewedOn": "2026-10-…"
}
```

- `kind` is `text-match` or `error`. An `error` entry has no chunk lists. Its snapshot is `errorSide` (`baseline` or `candidate`) plus `errorCode` (for example `SQL7619` or `PG42601`).
- `category` is one of `tokenization`, `stop-words`, `punctuation`, `accents`, `error-handling` or `other`.
- `decision` is `acceptable` or `blocker`.
- An entry applies only if `baselineOnly` and `candidateOnly` match the observed difference **exactly**. If the difference changes, the entry no longer matches and the difference counts as unreviewed.
- A `blocker` entry fails the verdict. Recording blockers keeps "we checked, and this would break users" as part of the answer.

### 7.5 `RESULTS.md`

`compare --out RESULTS.md` writes:
1. **The verdict** and the five conditions, each marked pass or fail with its value.
2. **Environment:**
   - SQL Server image digest, `@@VERSION`, full-text language and stoplist;
   - Postgres `version()`, pgvector version and text search configuration;
   - data manifest commit and hashes;
   - the sample's git commit and dirty flag;
   - the thresholds.
3. **Rule 1:** a summary, plus every failure.
4. **Rule 2:** a summary, plus each difference with snippets, tokenization, and the matching known-differences entry or "UNREVIEWED".
5. **Rule 3:** the metrics, a per-pair table, and every difference with its category.
6. **Informational:**
   - the quirk-fixed run on both engines (the same metrics);
   - `postgres-english` against `sqlserver`: the extra matches from stemming and the overlap.

   Each part says "not seeded" if its database is missing.
7. **Errors:** every error result, with its known-differences status.

The console version prints the same summary block followed by the failures. Live queries (`compare --query "<text>"`) print a side-by-side comparison for that one query and never produce a verdict or `RESULTS.md`.

## 8. CLI

| Command | Purpose |
|---|---|
| `generate-data [--corpus-commit 9f8cd102]` | Read the corpus from git, sanitize and chunk it, add the edge cases, embed everything, compute ground truth, and write `data/` and the manifest. Needs `OPENAI_API_KEY` |

- `0`: success. For `compare`, the verdict is switchable.
- `1`: `compare` ran, and the verdict is not switchable.
- `2`: a configuration, data or connection error.

## 9. Testing

### 9.1 Unit tests (no Docker)

Written test-first. They cover:
- tie grouping;
- overlap@5 and same-#1, including tie groups that straddle position 5;
- each explanation category, plus the unexplained case;
- matching against `known-differences.json`: exact snapshot, changed snapshot and blocker;
- the verdict and its thresholds;
- round-tripping the data files, which must preserve float32 values bit for bit;
- the v5 GUIDs;
- the copied `ChunkText`, on hand-built inputs at the 2,048-byte boundary, the overlap step and the early-exit rule.

### 9.2 Integration tests (`Category=Integration`, Testcontainers)

- **Setup:** a single fixture starts `ghcr.io/elumenotion/mssql2025-express-fts:main` and `pgvector/pgvector:0.8.7-pg18` once, seeds `sqlserver` and `postgres`, and runs the full comparison in-process.
- **The tests assert:**
  - rule 1 passes;
  - rule 2 passes once `known-differences.json` is applied;
  - there are zero unexplained hybrid differences.
- **The tests don't assert the verdict thresholds.** The verdict is the experiment's result, not a measure of whether the code is correct.
- **Sanity checks that stop a false pass:**
  - SQL Server's full-text item count equals the row count;
  - Postgres's `"ContentTsv"` is non-empty for every non-empty chunk;
  - for every exact-phrase and edge-case query with a non-empty ground truth, each engine's match set is non-empty and overlaps the ground truth;
  - for every exact-phrase query, at least one scope has a ground-truth chunk in each engine's hybrid top 5.
- **Copy-drift check:** the SHA-256 of `HybridSearcher.cs`, `HybridIndexer.cs` and `MarkdownInlineImageSanitizer.cs` in the working tree must equal the values recorded at `9f8cd102`:

## 11. Error handling

The CLI stops with exit code 2 and a specific message for:
- an unknown or missing profile or provider (it lists the valid names);
- a database that can't be reached (it names the profile and host);
- missing or mismatched data files (it says to run `generate-data` or restore `data/`);
- a vector that isn't 1536 dimensions;
- SQL Server full-text not being installed;
- full-text population timing out;
- live query text with no API key.

`generate-data` retries OpenAI 429 and 5xx responses with exponential backoff, and stops after repeated failures without writing partial data. Output is written to a temporary folder and moved into place only when complete.

- Whether `ts_rank_cd` with normalization 32 is the closest equivalent of `RANK / 1000`. It's fixed for the verdict run. If rule 3 shows systematic score-scale effects, that's a finding, not something to tune away.
